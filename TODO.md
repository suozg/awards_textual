## 2. В «Звітах» выбранный статус вручения сейчас не влияет на SQL

В `ZvitTab` есть селектор `handover_status`, значения «призначені», «видані» и «залишок в натурі», а `_collect_filters()` включает его в фильтры. Но `_fetch_rows()` не применяет это значение к запросу. То есть пользователь меняет статус, а результат отчёта по этому фильтру остаётся прежним. Код находится в [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L398-L422) и [`_fetch_rows()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L464-L630).

После формирования основного запроса и до `cursor.execute()` добавьте обработку статуса. В wx-версии остаток и выданные награды дополнительно фильтруются по накладной, а назначенные обрабатываются иначе — ориентируйтесь на нужную бизнес-логику при переносе:

```python name=zvity_textual.py
if not has_submission_status_filter:
    handover_status = filters["handover_status"]

    if handover_status == AWARD_HANDOVER_STATUS_REMAINING:
        query += """
            AND m.consignment_note IS NOT NULL
            AND TRIM(m.consignment_note) != ''
            AND (m.handover IS NULL OR TRIM(m.handover) = '')
        """
    elif handover_status == AWARD_HANDOVER_STATUS_ISSUED:
        query += """
            AND m.consignment_note IS NOT NULL
            AND TRIM(m.consignment_note) != ''
            AND m.handover IS NOT NULL
            AND TRIM(m.handover) != ''
        """
    elif handover_status == AWARD_HANDOVER_STATUS_ASSIGNED:
        # Сверьте точное определение «призначені» с текущей бизнес-логикой wx.
        pass
```

Обратите внимание: в wx-версии фильтр периода для остатка (`status == 1`) устроен не так, как для остальных статусов. Не переносите диапазон дат автоматически, не решив, какое поведение нужно сохранить.

### Отдельно проверьте фильтр «відсутні протоколи видачі»

Сейчас он добавляет условие «поле `handover` пусто» — это похоже на фильтр по неврученным наградам, а не по отсутствию протокола. В коде карточки `$` используется как отметка наличия протокола: `handover.endswith("$")`. Если это по-прежнему фактическое правило хранения, условие для выданной награды без протокола должно отличать заполненное поле получателя от маркера `$`:

```python name=zvity_textual.py
if filters["issue_protocols"]:
    query += """
        AND m.handover IS NOT NULL
        AND TRIM(m.handover) != ''
        AND SUBSTR(m.handover, -1, 1) != '$'
    """
```

Перед применением подтвердите, что `$` — единственный и актуальный признак протокола в данных. В старом wx-коде фильтр ещё учитывает ранги наград; его поведение стоит сверить отдельно.

## 3. Отчёт «Усі» может пропускать подання без награждения

При статусе подання «Усі» `_fetch_rows()` строит запрос от таблицы `meed` и присоединяет `presentation`. Такой запрос по своей структуре не включает подання, у которых нет связанного награждения. Для статусов «Погоджені», «Не погоджені» и «У залишку» запрос уже строится от `presentation`.

В wx-версии есть отдельное переключение режима «Нагородження / Подання»; в Textual в форме один смешанный отчёт. См. ветвление `FROM presentation` / `FROM meed` в [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L476-L521) и фильтр статуса ниже по этому же методу.

**Рекомендация:** вернуть в Textual явный режим отчёта, как в wx, и строить запрос под выбранный режим. Это проще проверить, чем пытаться решить оба сценария одним неявным `LEFT JOIN`. Если нужен именно общий отчёт «всё вместе», отдельно спроектируйте объединение награждений и подань и проверьте, как обрабатывать несколько подань на одну награду, чтобы не получить дубликаты.

## 4. Соединение `handover` с получателем может не находить человека

В отчёте поле получателя связывается так:

```sql
LEFT JOIN personality p2 ON p2.id = m.handover
```

Но в других местах приложения значение `handover` очищается от завершающего `$` перед поиском получателя. Если в базе хранится, например, `123$`, соединение по исходному значению может не найти `p2.name` и показать вместо имени необработанный идентификатор.

Проверьте это на записи с протоколом. Если формат данных подтверждён, измените условие соединения:

```python name=zvity_textual.py
LEFT JOIN personality p2
    ON p2.id = RTRIM(m.handover, '$')
```

Такой же принцип уже используется в запросе наград для поиска: [`database_logic_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/database_logic_textual.py#L164-L179).

## 5. Удаление и сохранение в карточке не обновляют список найденных данных

`KartkaTab.on_save()` записывает изменения в БД, но после успешного сохранения не перечитывает текущую особу, подання и награждения. В результате список и поля карточки могут остаться устаревшими до нового поиска или другого ручного обновления. В wx для этого есть повторный поиск после операций карточки: [`trigger_search_in_tab1_and_load_results()`](https://github.com/suozg/awardswx/blob/aac95609775f2a00d28222f1b16b0b21b0fdf0ec/kartka.py#L2060-L2068).

**Что добавить:** после успешного сохранения или связывания повторно загрузить данные текущего человека и обновить содержимое карточки. В `database_logic_textual.search_q()` уже предусмотрен аргумент `search_id`, поэтому можно перечитать конкретную запись, не выполняя поиск по введённой строке. При этом не обязательно заменять весь исходный список результатов: обновите данные выбранного человека внутри сохранённого снимка поиска.

Аналогично, после изменений через SQL-вкладку другие вкладки не получают сигнал об изменениях. После ручного `UPDATE` или `DELETE` пользователь может видеть прежние результаты, пока не выполнит обновление. Это хороший кандидат на простую кнопку «Обновить» или централизованное обновление данных после SQL-запроса, меняющего БД.

## 6. CSV в Textual — это фильтр, а не полный аналог сравнения CSV из wx

`CsvPersonFilter` загружает нормализованные РНОКПП, а `_fetch_rows()` фильтрует отчёт через `p.inn IN (...)`. В wx есть отдельный сценарий сравнения списка людей с данными базы, с нормализацией ПІБ/РНОКПП, выбором формата сравнения и экспортом результата. Сравните [`CsvPersonFilter`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/csv_person_filter.py#L56-L103) с [`ComparisonReportFrame` в wx](https://github.com/suozg/awardswx/blob/aac95609775f2a00d28222f1b16b0b21b0fdf0ec/ui_utils.py#L174-L233).

Это не обязательно дефект, если в Textual планировался только фильтр. Но это **не эквивалентная замена сравнения**: совпадение проверяется по ИНН в SQL, а отдельного результата «человек из CSV найден/не найден, какие у него награды» здесь нет.

Также проверьте в `load_person_inns_from_csv()` файл с заголовком, где подходящий столбец пуст, но значения есть в другой колонке. Сейчас резервный разбор первого столбца запускается только при пустом общем множестве `values`; поведение для такого файла может оказаться неожиданным.

## 7. Довідник позволяет создать категории, но остальные вкладки используют фиксированный список

`DovidnykTab` разрешает создавать категорию с `ranking = max(...) + 1`; названия и описания категорий при этом хранятся отдельно в `~/.config/awards_textual/categories.json`. Но `RankingValues` в `database_logic_textual.py` фиксирован и содержит только заранее известные ранги. Отчёты и карточка используют этот список для отображения и фильтрации наград.

В результате новая категория в довіднику может появиться в дереве, но не получить ожидаемое отображение или фильтр в остальных вкладках. Логика добавления категории — [`dovidnyk_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/dovidnyk_textual.py#L287-L299), загрузка рангов наград в отчёте — [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L174-L207).

**Пока не разрешайте произвольные новые ранги**, если остальные вкладки не умеют их читать. Варианты: оставить существующие категории и разрешить менять только их локальные подписи; либо договориться о едином источнике категорий и обновить всех потребителей ранга, включая отчёты и карточку. Учтите, что `categories.json` находится на конкретном компьютере, а не в SQL-базе, поэтому пользователь на другом компьютере может увидеть другие названия.


## 9. Долгие запросы выполняются в UI-потоке Textual

Поиск объявлен асинхронным, но `search_q()` и загрузка изображений выполняются непосредственно внутри `run_search()`. Аналогично, `refresh_report()` синхронно выполняет SQL и заполняет таблицу. Само наличие `async def` не переносит блокирующий SQLite-запрос в отдельный поток. См. [`SearchTab.run_search()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/search_tab_textual.py#L150-L175) и [`ZvitTab.refresh_report()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L424-L462).

На небольшой базе это может быть незаметно. На большой — интерфейс может «замирать». Если выносить запросы в worker, не используйте один и тот же курсор параллельно из разных потоков: открывайте соединение и курсор для worker отдельно, как wx-версия делает для фоновой загрузки отчётов.

## Что уже есть в Textual и что выглядит как незавершённый порт

- В Textual есть FTS-вкладка, SQL, законы и редактор довідника; это полезные части, не требующие автоматического переписывания.
- Просмотренный CSV-код Textual реализует фильтрацию по ИНН, но не весь сценарий сравнения CSV из wx.
- Для репозитория Textual в полученном списке корневых файлов не видно отдельного набора тестов или файла зависимостей. README пока содержит только название проекта и описание порта: [README.md](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/README.md).


## Проверки перед исправлениями

Проводите тесты на **копии** базы, особенно для SQL, удаления и связывания записей.

1. В «Картці» удалить человека с несколькими поданнями и награждениями; проверить подтверждение и отсутствие записей-сирот.
2. Для каждого статуса вручения сформировать отчёт и проверить, что список действительно меняется.
3. Проверить выданную награду с `handover` в виде ID и с ID, заканчивающимся на `$`: отчёт должен корректно показывать имя получателя и статус протокола.
4. Для статуса подання «Усі» проверить человека с поданнями без связанной награды.
5. Сохранить изменения карточки и убедиться, что выбранная особа и связанные списки обновились без повторного ручного поиска.
6. Загрузить CSV с заголовками, с пустым ИНН и с РНОКПП, сохранённым как число; проверить, какие строки попадают в фильтр.
7. Создать тестовую категорию в довіднику и проверить, как она отображается в отчётах и карточке.
8. Запустить большой поиск и отчёт и оценить, остаётся ли интерфейс отзывчивым.

**Порядок исправлений, который я бы выбрал:** 
1. сначала удаление связанной записи и реальные фильтры отчёта; 
2. затем обновление карточки после сохранения и проверка режима «Усі»; 
3. затем пароль по умолчанию и регрессионные тесты.
4. Новые категории, вебпоиск и полное сравнение CSV — после уточнения, входят ли они в ожидаемый объём Textual-порта.




## Дальние плани

**Для веб-доступа не стоит просто публиковать текущий `AwardsTextualApp`.** Сейчас вкладки напрямую используют общий SQLCipher `cursor` и выполняют SQL внутри UI-классов. Для нескольких пользователей нужен серверный слой, который сам проверяет личность и права **до** чтения или изменения данных.

Рекомендую оставить Textual как настольный клиент, а для браузера добавить API-сервер и веб-интерфейс. Оба клиента смогут использовать общий слой бизнес-логики. Это заметная работа, но именно она позволит надёжно применять роли и вести аудит: проверки только на уровне кнопок или вкладок можно обойти.

## Что видно в текущей реализации

- Подключение к базе создаётся в `main_textual.py`; приложение хранит общие `self.conn` и `self.cursor` — [подключение и состояние приложения](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/main_textual.py#L170-L203).
- Вкладки получают соединение напрямую. Например, `KartkaTab` выполняет `INSERT`, `UPDATE` и `DELETE` самостоятельно — [`KartkaTab.on_save()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/kartka_textual.py#L618-L750).
- SQL-вкладка выполняет произвольный введённый SQL и фиксирует запросы без результата `commit()`-ом — [`execute_sql()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/main_textual.py#L381-L419). Для веб-режима это критичный обход любых прав доступа, если оставить такой доступ обычным пользователям.
- В `config.py` задан `MASTERKEY = '1'`; секрет нельзя хранить в исходниках или в клиентском приложении — [`config.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/config.py#L1-L9).
- Доступный README пока не описывает веб-сервер или развёртывание — [README.md](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/README.md).

## План перехода

### 1. Сначала определить модель доступа

Если несколько пользователей должны работать с одной базой, держите базу и ключ SQLCipher **только на сервере**. Браузер должен обращаться к API по HTTPS — не к файлу БД и не к SQLCipher напрямую.

Для начала хватит трёх ролей:

| Роль | Возможности |
|---|---|   
| `reader` | Поиск, карточки и отчёты без изменений |
| `editor` | Чтение и создание/изменение записей |
| `admin` | Управление пользователями, настройками и ограниченными административными операциями |

Операции удаления лучше выделить отдельно или разрешить только `admin`, пока не проверите процесс подтверждения и журналирования. Не передавайте роль от браузера в теле запроса: сервер должен получать её из учётной записи пользователя.

### 2. Убрать секреты из `config.py`

В `config.py` не должно быть рабочего пароля, ключа базы или мастер-пароля. Настройте их в переменных окружения сервера или в хранилище секретов:

```python name=конфигурация_сервера.py
import os

DATABASE_FILE_PATH = os.environ["AWARDS_DB_PATH"]
DATABASE_KEY = os.environ["AWARDS_DB_KEY"]
SESSION_SECRET = os.environ["AWARDS_SESSION_SECRET"]
```

При старте сервера проверьте, что секреты заданы; если нет — завершите запуск с ошибкой. Не добавляйте `.env` с рабочими значениями в Git. Для первого администратора сделайте отдельную CLI-команду создания учётной записи, а не стандартный логин и пароль.

### 3. Вынести операции из вкладок в общий сервисный слой

Создайте, например:

```text
api/
  app.py
  dependencies.py
  routes/
    auth.py
    people.py
    reports.py
    awards.py
services/
  people_service.py
  report_service.py
  award_service.py
repositories/
  people_repository.py
  report_repository.py
  audit_repository.py
security/
  passwords.py
  sessions.py
migrations/
```

Перенесите SQL и транзакции из UI-классов в сервисы и репозитории. Начать можно с операций карточки: запись человека, подання, награждения, связывание и удаление. Затем перенести запрос отчёта из `ZvitTab._fetch_rows()` и операции справочника и законов.

В результате обработчик UI/API будет вызывать сервис, а не выполнять SQL:

```python name=services/people_service.py
def update_person(repository, actor, person_id, values):
    # Здесь проверяются бизнес-условия изменения.
    # repository выполняет SQL с параметрами.
    return repository.update_person(person_id, values)
```

**Важно:** эта проверка — не замена авторизации. Сервис или API-обработчик должен получить `actor` из проверенной сервером сессии, а не из запроса клиента.

### 4. Добавить пользователей, пароли и серверные сессии

Добавьте миграцию БД с таблицами `app_user` и `web_session`. В таблице пользователей храните хеш пароля, роль и признак активности; пароль открытым текстом не сохраняйте. Для хеширования используйте Argon2id, например через `pwdlib[argon2]` или `argon2-cffi`.

Для браузера предпочтительна серверная сессия с непредсказуемым токеном в cookie `HttpOnly`, `Secure`, `SameSite=Lax`; в БД храните хеш токена и срок его действия. Не кладите токен в `localStorage`. Для изменяющих запросов добавьте CSRF-защиту. Также нужны ограничение частоты попыток входа и возможность отзывать сессии пользователя.

Если позже выберете JWT вместо серверных сессий, понадобится отдельная проработка сроков жизни, обновления и отзыва токенов. Для первого веб-запуска серверные сессии обычно проще отозвать и контролировать.

### 5. Проверять права на сервере для каждого маршрута

Например, заведите центральный список разрешений:

```python name=security/permissions.py
ROLE_PERMISSIONS = {
    "reader": {
        "people:read",
        "reports:read",
    },
    "editor": {
        "people:read",
        "people:write",
        "reports:read",
    },
    "admin": {"*"},
}


def has_permission(role: str, permission: str) -> bool:
    permissions = ROLE_PERMISSIONS.get(role, set())
    return "*" in permissions or permission in permissions
```

В FastAPI проверки можно оформить зависимостью, применяемой к маршрутам:

```python name=api/dependencies.py
from fastapi import Depends, HTTPException, status

from security.permissions import has_permission


def require_permission(permission: str):
    def check(user=Depends(get_current_user)):
        if not has_permission(user.role, permission):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Недостатньо прав",
            )
        return user

    return check
```

И использовать её на каждом серверном endpoint:

```python name=api/routes/people.py
@router.get("/{person_id}")
def get_person(
    person_id: int,
    user=Depends(require_permission("people:read")),
):
    return people_service.get_person(person_id)


@router.put("/{person_id}")
def update_person(
    person_id: int,
    payload: PersonUpdate,
    user=Depends(require_permission("people:write")),
):
    return people_service.update_person(
        actor=user,
        person_id=person_id,
        values=payload,
    )
```

`get_current_user` здесь должен проверять cookie-сессию и загружать пользователя с сервера. Не доверяйте `user_id`, `role` или признаку «администратор», пришедшим от клиента.

### 6. Добавить аудит действий

Создайте таблицу `audit_log` через миграцию, а не только в форме интерфейса. Минимальный состав полей:

```sql
CREATE TABLE audit_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    occurred_at TEXT NOT NULL,
    actor_user_id INTEGER,
    action TEXT NOT NULL,
    entity_type TEXT,
    entity_id TEXT,
    outcome TEXT NOT NULL,
    request_id TEXT,
    details_json TEXT
);
```

Пишите в журнал как минимум:

- успешный и неуспешный вход, выход и блокировку пользователя;
- создание, изменение, связывание и удаление людей, подань и награждений;
- изменение пользователей, ролей и настроек;
- запуск административных операций;
- отказ в доступе, если он важен для расследования.

Для успешной записи данных и соответствующей audit-записи используйте одну транзакцию: либо фиксируются обе, либо ни одна. Ошибку записи в журнал нельзя молча игнорировать. Для неуспешных входов данные аудита записывайте отдельно от транзакции изменения предметных данных.

**Не записывайте** пароли, ключ SQLCipher, содержимое сессии, полный текст подання, РНОКПП и целиком тело запроса. Для журнала достаточно ID записи, типа действия, результата и ограниченных метаданных. Audit-таблица в той же SQLCipher-базе защищена шифрованием БД, но не становится неизменяемой: администратор сервера с доступом к файлу может её изменить. Для более строгих требований отправляйте копии журнала в отдельное защищённое хранилище.

### 7. Закрыть прямой доступ к SQL-консоли

Не подключайте текущую SQL-вкладку в общедоступный веб-интерфейс. Сейчас `execute_sql()` выполняет SQL пользователя непосредственно и делает `commit()` для запросов без набора результатов. Это обходит ролевые ограничения API.

Лучший вариант — не публиковать SQL-консоль в веб-версии. Если она нужна администраторам, вынесите её в отдельный обслуживающий инструмент с отдельным доступом и журналированием. Ограничение только проверкой строки на `SELECT` не является достаточной защитой: для безопасного read-only режима нужны отдельное соединение с запретом записи и серверные ограничения на доступные таблицы и запросы.

### 8. Не делить один `cursor` между веб-запросами

Текущий `self.cursor` подходит для текущей модели одного UI-приложения, но не должен стать глобальным курсором FastAPI. Открывайте соединение и курсор на время запроса или операции и закрывайте их после завершения. Изменения выполняйте в явных транзакциях.

SQLite/SQLCipher допускает только ограниченную конкурентность записи. Для одного сервера и умеренного числа пользователей можно начать с SQLite, `WAL`, таймаута блокировки и сериализации пишущих операций. Если ожидаются частые параллельные изменения, отдельно оцените серверную СУБД. Ни в одном случае не допускайте, чтобы разные пользователи напрямую открывали общий файл базы по сетевой папке.

### 9. Подключить Textual и веб-клиент к сервисам

В настольном Textual-варианте вкладки постепенно переводятся с прямых SQL-вызовов на общий сервисный слой. Для веба браузерный UI вызывает API, а API — тот же сервисный слой. При этом роли проверяются на сервере независимо от того, какой клиент отправил запрос.

Если под «веб-режимом» имеется в виду именно отображение Textual-интерфейса в браузере, сначала отдельно проверьте выбранный способ запуска Textual через браузер. Но даже при сохранении Textual UI нельзя переносить SQLCipher-ключ и проверки авторизации на клиент: сервер должен оставаться единственной точкой доступа к базе.

## Порядок внедрения

1. Убрать рабочий ключ из кода и определить роли и разрешения.
2. Добавить миграции пользователей, сессий и `audit_log`.
3. Вынести SQL и транзакции карточки в сервисы; покрыть тестами запись, связывание и удаление.
4. Реализовать вход, серверную сессию, CSRF-защиту и проверку разрешений.
5. Добавить API для поиска, карточки и отчётов; проверять права на каждом endpoint.
6. Добавить аудит операций и административный CLI для создания/блокировки пользователей.
7. Подключить веб-интерфейс; не выдавать ему SQLCipher-ключ.
8. Отключить публичный SQL-интерфейс и закрыть сервер HTTPS, ограничить доступ к нему сетью/VPN, настроить резервное копирование.
9. Проверить систему на копии базы: `reader` не меняет записи, `editor` не управляет пользователями, блокировка учётной записи прекращает доступ, все успешные изменения попадают в журнал.

Для первого запуска я бы ограничил веб-версию внутренней сетью или VPN, запретил SQL-консоль и оставил только роли `reader` и `editor`, добавив `admin` после тестирования управления пользователями и аудита.
