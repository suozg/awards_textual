## 1. В первую очередь — удаление человека в «Картці»

В Textual при удалении человека выполняется только:

```python
DELETE FROM personality WHERE id = ?
```

При этом связанные записи `presentation` и `meed` не удаляются. В wx-версии перед удалением человека запрашивается подтверждение, затем удаляются связанные подання и нагородження, и только потом сама особа. Сравните [`KartkaTab.on_save()` в Textual](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/kartka_textual.py#L618-L642) и [`delete_personality()` в wx](https://github.com/suozg/awardswx/blob/aac95609775f2a00d28222f1b16b0b21b0fdf0ec/kartka.py#L1449-L1487).

**Что изменить:** перед удалением показывать подтверждение с количеством связанных записей; удаление всех трёх типов записей выполнять в одной транзакции. Пример тела операции:

```python name=kartka_textual.py
def delete_person_with_related_records(self, person_id: int) -> None:
    try:
        self.cursor.execute(
            "DELETE FROM presentation WHERE id_personality = ?",
            (person_id,),
        )
        self.cursor.execute(
            "DELETE FROM meed WHERE id_personality = ?",
            (person_id,),
        )
        self.cursor.execute(
            "DELETE FROM personality WHERE id = ?",
            (person_id,),
        )
        self.conn.commit()
    except sqlite3.Error:
        self.conn.rollback()
        raise
```

Этот метод следует вызывать **только после подтверждения пользователем**. Удаление подання и нагородження тоже стоит сверить с wx-логикой: там учитываются связанные записи, а в Textual сейчас удаляется только выбранная строка.

## 2. В «Звітах» выбранный статус вручения сейчас не влияет на SQL

В `ZvitTab` есть селектор `handover_status`, значения «призначені», «видані» и «залишок в натурі», а `_collect_filters()` включает его в фильтры. Но `_fetch_rows()` не применяет это значение к запросу. То есть пользователь меняет статус, а результат отчёта по этому фильтру остаётся прежним. Код находится в [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L398-L422) и [`_fetch_rows()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L464-L630).

После формирования основного запроса и до `cursor.execute()` добавьте обработку статуса. В wx-версии остаток и выданные награды дополнительно фильтруются по накладной, а назначенные обрабатываются иначе — ориентируйтесь на нужную бизнес-логику при переносе:

```python name=zvity_textual.py
if not has_submission_status_filter:
    handover_status = filters["handover_status"]

    if handover_status == AWARD_HANDOVER_STATUS_REMAINING:
        query += """
            AND m.consignment_note IS NOT NULL
            AND TRIM(m.consignment_note) != ''
            AND (m.handover IS NULL OR TRIM(m.handover) = '')
        """
    elif handover_status == AWARD_HANDOVER_STATUS_ISSUED:
        query += """
            AND m.consignment_note IS NOT NULL
            AND TRIM(m.consignment_note) != ''
            AND m.handover IS NOT NULL
            AND TRIM(m.handover) != ''
        """
    elif handover_status == AWARD_HANDOVER_STATUS_ASSIGNED:
        # Сверьте точное определение «призначені» с текущей бизнес-логикой wx.
        pass
```

Обратите внимание: в wx-версии фильтр периода для остатка (`status == 1`) устроен не так, как для остальных статусов. Не переносите диапазон дат автоматически, не решив, какое поведение нужно сохранить.

### Отдельно проверьте фильтр «відсутні протоколи видачі»

Сейчас он добавляет условие «поле `handover` пусто» — это похоже на фильтр по неврученным наградам, а не по отсутствию протокола. В коде карточки `$` используется как отметка наличия протокола: `handover.endswith("$")`. Если это по-прежнему фактическое правило хранения, условие для выданной награды без протокола должно отличать заполненное поле получателя от маркера `$`:

```python name=zvity_textual.py
if filters["issue_protocols"]:
    query += """
        AND m.handover IS NOT NULL
        AND TRIM(m.handover) != ''
        AND SUBSTR(m.handover, -1, 1) != '$'
    """
```

Перед применением подтвердите, что `$` — единственный и актуальный признак протокола в данных. В старом wx-коде фильтр ещё учитывает ранги наград; его поведение стоит сверить отдельно.

## 3. Отчёт «Усі» может пропускать подання без награждения

При статусе подання «Усі» `_fetch_rows()` строит запрос от таблицы `meed` и присоединяет `presentation`. Такой запрос по своей структуре не включает подання, у которых нет связанного награждения. Для статусов «Погоджені», «Не погоджені» и «У залишку» запрос уже строится от `presentation`.

В wx-версии есть отдельное переключение режима «Нагородження / Подання»; в Textual в форме один смешанный отчёт. См. ветвление `FROM presentation` / `FROM meed` в [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L476-L521) и фильтр статуса ниже по этому же методу.

**Рекомендация:** вернуть в Textual явный режим отчёта, как в wx, и строить запрос под выбранный режим. Это проще проверить, чем пытаться решить оба сценария одним неявным `LEFT JOIN`. Если нужен именно общий отчёт «всё вместе», отдельно спроектируйте объединение награждений и подань и проверьте, как обрабатывать несколько подань на одну награду, чтобы не получить дубликаты.

## 4. Соединение `handover` с получателем может не находить человека

В отчёте поле получателя связывается так:

```sql
LEFT JOIN personality p2 ON p2.id = m.handover
```

Но в других местах приложения значение `handover` очищается от завершающего `$` перед поиском получателя. Если в базе хранится, например, `123$`, соединение по исходному значению может не найти `p2.name` и показать вместо имени необработанный идентификатор.

Проверьте это на записи с протоколом. Если формат данных подтверждён, измените условие соединения:

```python name=zvity_textual.py
LEFT JOIN personality p2
    ON p2.id = RTRIM(m.handover, '$')
```

Такой же принцип уже используется в запросе наград для поиска: [`database_logic_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/database_logic_textual.py#L164-L179).

## 5. Удаление и сохранение в карточке не обновляют список найденных данных

`KartkaTab.on_save()` записывает изменения в БД, но после успешного сохранения не перечитывает текущую особу, подання и награждения. В результате список и поля карточки могут остаться устаревшими до нового поиска или другого ручного обновления. В wx для этого есть повторный поиск после операций карточки: [`trigger_search_in_tab1_and_load_results()`](https://github.com/suozg/awardswx/blob/aac95609775f2a00d28222f1b16b0b21b0fdf0ec/kartka.py#L2060-L2068).

**Что добавить:** после успешного сохранения или связывания повторно загрузить данные текущего человека и обновить содержимое карточки. В `database_logic_textual.search_q()` уже предусмотрен аргумент `search_id`, поэтому можно перечитать конкретную запись, не выполняя поиск по введённой строке. При этом не обязательно заменять весь исходный список результатов: обновите данные выбранного человека внутри сохранённого снимка поиска.

Аналогично, после изменений через SQL-вкладку другие вкладки не получают сигнал об изменениях. После ручного `UPDATE` или `DELETE` пользователь может видеть прежние результаты, пока не выполнит обновление. Это хороший кандидат на простую кнопку «Обновить» или централизованное обновление данных после SQL-запроса, меняющего БД.

## 6. CSV в Textual — это фильтр, а не полный аналог сравнения CSV из wx

`CsvPersonFilter` загружает нормализованные РНОКПП, а `_fetch_rows()` фильтрует отчёт через `p.inn IN (...)`. В wx есть отдельный сценарий сравнения списка людей с данными базы, с нормализацией ПІБ/РНОКПП, выбором формата сравнения и экспортом результата. Сравните [`CsvPersonFilter`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/csv_person_filter.py#L56-L103) с [`ComparisonReportFrame` в wx](https://github.com/suozg/awardswx/blob/aac95609775f2a00d28222f1b16b0b21b0fdf0ec/ui_utils.py#L174-L233).

Это не обязательно дефект, если в Textual планировался только фильтр. Но это **не эквивалентная замена сравнения**: совпадение проверяется по ИНН в SQL, а отдельного результата «человек из CSV найден/не найден, какие у него награды» здесь нет.

Также проверьте в `load_person_inns_from_csv()` файл с заголовком, где подходящий столбец пуст, но значения есть в другой колонке. Сейчас резервный разбор первого столбца запускается только при пустом общем множестве `values`; поведение для такого файла может оказаться неожиданным.

## 7. Довідник позволяет создать категории, но остальные вкладки используют фиксированный список

`DovidnykTab` разрешает создавать категорию с `ranking = max(...) + 1`; названия и описания категорий при этом хранятся отдельно в `~/.config/awards_textual/categories.json`. Но `RankingValues` в `database_logic_textual.py` фиксирован и содержит только заранее известные ранги. Отчёты и карточка используют этот список для отображения и фильтрации наград.

В результате новая категория в довіднику может появиться в дереве, но не получить ожидаемое отображение или фильтр в остальных вкладках. Логика добавления категории — [`dovidnyk_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/dovidnyk_textual.py#L287-L299), загрузка рангов наград в отчёте — [`zvity_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L174-L207).

**Пока не разрешайте произвольные новые ранги**, если остальные вкладки не умеют их читать. Варианты: оставить существующие категории и разрешить менять только их локальные подписи; либо договориться о едином источнике категорий и обновить всех потребителей ранга, включая отчёты и карточку. Учтите, что `categories.json` находится на конкретном компьютере, а не в SQL-базе, поэтому пользователь на другом компьютере может увидеть другие названия.

## 8. Удалить пароль по умолчанию из `config.py`

В Textual сейчас задано `MASTERKEY = '1'`. При его наличии приложение пропускает обычный ввод пароля и использует заданный ключ автоматически. Это значение нельзя оставлять в рабочей версии. См. [`config.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/config.py#L1-L9) и обработку запуска в [`main_textual.py`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/main_textual.py#L205-L225).

Для обычного запуска:

```python name=config.py
MASTERKEY = None
```

Тогда приложение использует экран ввода пароля.

## 9. Долгие запросы выполняются в UI-потоке Textual

Поиск объявлен асинхронным, но `search_q()` и загрузка изображений выполняются непосредственно внутри `run_search()`. Аналогично, `refresh_report()` синхронно выполняет SQL и заполняет таблицу. Само наличие `async def` не переносит блокирующий SQLite-запрос в отдельный поток. См. [`SearchTab.run_search()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/search_tab_textual.py#L150-L175) и [`ZvitTab.refresh_report()`](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/zvity_textual.py#L424-L462).

На небольшой базе это может быть незаметно. На большой — интерфейс может «замирать». Если выносить запросы в worker, не используйте один и тот же курсор параллельно из разных потоков: открывайте соединение и курсор для worker отдельно, как wx-версия делает для фоновой загрузки отчётов.

## Что уже есть в Textual и что выглядит как незавершённый порт

- В Textual есть FTS-вкладка, SQL, законы и редактор довідника; это полезные части, не требующие автоматического переписывания.
- В просмотренной сборке `MainScreen` нет вкладки вебпоиска указов, которая есть в wx (`websearch.py`).
- Просмотренный CSV-код Textual реализует фильтрацию по ИНН, но не весь сценарий сравнения CSV из wx.
- Для репозитория Textual в полученном списке корневых файлов не видно отдельного набора тестов или файла зависимостей. README пока содержит только название проекта и описание порта: [README.md](https://github.com/suozg/awards_textual/blob/9b9a523747c1b619f145cc457188726d9326d872/README.md).

Это не означает, что все эти функции обязательно нужно добавлять: сначала стоит решить, какие возможности wx должны быть в Textual по замыслу проекта.

## Проверки перед исправлениями

Проводите тесты на **копии** базы, особенно для SQL, удаления и связывания записей.

1. В «Картці» удалить человека с несколькими поданнями и награждениями; проверить подтверждение и отсутствие записей-сирот.
2. Для каждого статуса вручения сформировать отчёт и проверить, что список действительно меняется.
3. Проверить выданную награду с `handover` в виде ID и с ID, заканчивающимся на `$`: отчёт должен корректно показывать имя получателя и статус протокола.
4. Для статуса подання «Усі» проверить человека с поданнями без связанной награды.
5. Сохранить изменения карточки и убедиться, что выбранная особа и связанные списки обновились без повторного ручного поиска.
6. Загрузить CSV с заголовками, с пустым ИНН и с РНОКПП, сохранённым как число; проверить, какие строки попадают в фильтр.
7. Создать тестовую категорию в довіднику и проверить, как она отображается в отчётах и карточке.
8. Запустить большой поиск и отчёт и оценить, остаётся ли интерфейс отзывчивым.

**Порядок исправлений, который я бы выбрал:** 
1. сначала удаление связанной записи и реальные фильтры отчёта; 
2. затем обновление карточки после сохранения и проверка режима «Усі»; 
3. затем пароль по умолчанию и регрессионные тесты.
4. Новые категории, вебпоиск и полное сравнение CSV — после уточнения, входят ли они в ожидаемый объём Textual-порта.
